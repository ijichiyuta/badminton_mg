**長期目標はこの製品の代替である。** 潰すのではなく、**良いところを全て取り込んだ上で、
構造的に勝てない弱点で差をつける。**

調査日 2026-09-13。一次資料は公式サイト（autobad.net）の各ページと更新履歴、ドメイン登録情報。

## 5. 徹底的に取り込むべき「良いところ」

**ここが本書の目的。** 13年かけて現場に磨かれた設計であり、思いつきで超えられない。

### 5-1 設計コンセプトをそのまま引き継ぐ

> 設計コンセプトは、大会開催時に**人が頭を使わず**できるだけ自動化して試合を進行する、です
> 最終目標は**人の仕事がコートの準備、シャトル出しくらいになる**ことを目指しています

**この一文が正しい。** 本システムの `docs/13-operator-load.md`（運営負担の削減）は、
独立に導いた結論だが行き着く先は同じである。**言い換えずに、この定義を採用する。**

### 5-2 機能として必ず持つもの

| # | 機能 | なぜ外せないか | 本システムでの位置 |
|---|---|---|---|
| 1 | **自動進行モード**（結果入力 → 次の試合を自動判定 → スコアシート自動印刷） | この製品の核。運営者の判断を消す唯一の機能 | **v1 に入れる。** F-4-1 / F-9-5 を統合する |
| 2 | **Excel からの貼り付けで参加者登録** | ファイル選択を経由させない | F-2-2（実装済みの要件） |

| 4 | **タイムテーブルと組合せのWEBページ自動生成 + 途中経過のリアルタイム反映** | 選手・観戦者がアクセスする唯一の経路 | F-10。**v1 で当てにいく** |

## 6. 構造的に勝てる場所

取り込むだけでは代替にならない。**13年の蓄積で追いつけない部分ではなく、
この製品の構造そのものが許さない部分で差をつける。**

| # | 弱点 | 性質 | 本システムの立ち位置 |
|---|---|---|---|
| 1 | **Windows 専用・インストール必須** | 構造的 | ADR-0004。ブラウザで動く。協会の共用PCにインストール権限がなくても使える |
| 2 | **管理者権限が要る場面がある** | 構造的 | N-4-4 |
| 3 | **スマホ・タブレットで運営できない**（Androidアプリはスコア入力専用の従属物） | 構造的 | N-4-2。375px 幅で完全に運営できる |
| 4 | **2025年リリース0件。開発環境の移行に1年7ヶ月** | 現在進行 | 更新を止めない。Web なら審査もインストールもなく即日直る |
| 5 | **バス係数1** | 構造的 | 変わらない（こちらも1人）。ただし**JSONエクスポートで囲い込まない**ことは宣言できる |
| 6 | **有償テンプレート作成が必要 = 設定で吸収できていない** | 設計 | 要項プリセットとマトリクス一括編集で、**設定を増やさずに様式差を吸収する**（`docs/15-ui-ux.md`） |
| 7 | **順位決定ルールの設定自由度が不明** | 未確認 | **ここが本命。** 要項ごとに違う順位決定を、設定可能なルールエンジンで持つ（`docs/05`） |
| 8 | **選手・観戦者向けの体験がない** | 設計 | 運営者向けに閉じている。「自分の次の試合はいつ・どこか」に特化した閲覧ページで取る（F-10-5） |
| 9 | **判定根拠を説明する機能がない**（推定） | 設計 | 順位の根拠を人間が読める文で出す。**信用装置**（F-6-3） |

**1〜3 は13年かけても変えられない。** Windowsアプリとして作られた時点で決まっている。

## 6b. 申込・オーダーを巻き取るかどうか（2026-09-14 の検討）

### 結論：巻き取る。ただし部分的に取らない

**オーダー提出ページが成立するには「チームのメンバー名簿」が要る。**
チーム名を選ぶとメンバーが出てくる挙動は、名簿があって初めて動く。
そして**名簿は申込から来る**。

```
申込  →  名簿  →  オーダー  →  組合せ  →  集計  →  結果公開
       ↑ここを持つ者だけがオーダーを出せる
```

したがって **申込を持たずにオーダーだけ持つのは構造的に無理**であり、
逆に申込を持てばオーダーは自動的に持てる。**部分的に取るのが最も筋が悪い。**

他人のページから連携するには、スクレイピングするか先方にシステムを変えてもらうしかない。
前者は壊れやすく、後者は技術ではなく政治の話になる。
加えて、選手から見て「申込はここ、オーダーはあっち、結果はまた別」は
それ自体が問い合わせを生む。

### ただし責任が一段重くなる

| | 集計アプリ | 申込システム |
|---|---|---|
| データの置き場所 | 端末内 | サーバ必須 |
| 持つ個人情報 | 氏名・所属 | **住所・電話・年齢・会員番号** |
| 壊れたときの被害 | その大会が止まる | **個人情報が漏れる** |

申込書は住所と電話番号を集めている。数百人ぶんをサーバに置くのは別次元の責任。

### 順番

| # | やること | なぜこの順か |
|---|---|---|
| 1 | 集計で信頼を取る | 一番壊れていて、実データで再現を見せられる |
| 2 | 結果公開 | 電波があり、選手が見る文化もある。サーバの練習にもなる |
| 3 | 申込 | 一番壊れている。**ここで名簿を手に入れる** |
| 4 | オーダー | 名簿があれば自然に出てくる |

**1をやらずに3から入るのは危険。** まだ何も納品していない相手に
「申込も任せてください」は通らない。

### オーダーの運用が2種類ある可能性（要確認）

2026-09-14 の聞き取りで、新日本スポーツ連盟の大会では
**スコアシートだけ渡され、試合開始時にオーダーを記載していた**という証言が出た。

これが事実なら、**第1号提供先には「オーダー未提出」という状態が発生しない**。
「未提出チームを探して回るのが時間損失」という前提で設計していた機能が、
まるごと不要になる。

| 想定していた運用 | 証言された運用 |
|---|---|
| 事前提出 → 未提出チームを督促 | **その場で紙に書く** |
| オーダー提出ページ | スコアシートが戻ったときにオーダーも転記 |
| ホーム画面に未提出リスト | 不要 |

→ Q D-9 / D-10 で切り分ける。**要らない機能を作らずに済むなら、それが一番いい。**

### 7.1 BIRD SCORE は「一製品」ではない。協会そのものである

当初この表で BirdScore を「リアルタイムスコア表示システム」と書いていたが、**誤り**だった。
調べ直した結果は次のとおり。

| 項目 | 事実 |
|---|---|
| 開発 | テクノネット＋TMONY、**日本バドミントン協会監修** |
| リリース | 2021年3月 |
| 正式採用 | **第74回全日本総合**から協会公式のスコアシステムとして |
| 使用大会 | インターハイ、全国高校選抜、国体、S/Jリーグ |
| 範囲 | 審判のタブレット入力**だけではない**。選手リスト登録・PDF出力・ウェブサイト管理・進行管理・レフェリーコールまで含む**大会運営機能の統合**  |
| 入手 | JBA 会員サイトから「練習版」にアクセスできる |

※ **BIRD MEMBERS は別物。**あちらはファンクラブで、選手登録の会員登録システムとも違う。混同しない。

これが意味すること。

1. **「紙をやめて電子入力にする」という提案は、協会にとって新しくない。** 全国大会ではすでに標準。
   価値の主張を「電子化」に置くと、相手は「それ BIRD SCORE でやってる」と返せてしまう。
2. **上から降りてこない層が残っている。** BIRD SCORE が入るのは協会が主催する全国・県の公式戦。
   第1号提供先（新スポ連）のような**協会外のローカル大会**、
   および協会主催でも下位カテゴリの大会には降りてこない。**そこが本システムの居場所**。
3. **要項の多様性は BIRD SCORE では吸収できない。** 全国大会は21点3ゲームで固定できるが、
   ローカル大会は15点・17点上限・延長なしが同一団体内で並存する（`docs/00` P-02）。
   順位決定基準も団体ごとに違う。**設定可能性こそが差**であって、電子化は差ではない。
4. **競合として正面から戦う相手ではない。** 協会が監修しているものに機能で勝つ意味はない。
   すみ分ける。将来 BIRD SCORE 形式での出力が必要になる可能性は頭に置く。

**クラウド型（バドコンペクラウド）と無料（大会運営.net）はすでに存在する。**
「Webで動く」だけでは差にならない。差は **順位決定ルールエンジン** と **1人運用の負担削減** に置く。
