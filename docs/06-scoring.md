# 採点方式

## 前提

**国内大会は 3ゲーム×15点制へ移行する予定である。** 一方で、移行の完了時期は大会・団体によってばらつき、
当面は 21点制で開催される大会が併存する。
さらにローカル大会では、**時間短縮のために予選だけ1ゲーム制にする**といった運用が日常的に行われる。

したがって採点方式は次のように扱う。

1. **既定値は 15点3ゲーム制**
2. **21点制をはじめ、複数のプリセットから選べる**
3. **どの点数もハードコードしない。** `ScoringRuleSet` の値としてのみ参照する
4. **大会 → 種目 → ステージの3段階で上書きできる**

`21` や `30` という数値がドメイン層のコードに直接現れた時点で設計違反とする。

## ScoringRuleSet

| 項目 | 実装名 | 意味 |
|---|---|---|
| 勝敗の決め方 | `winCondition` | `POINTS`（点数で決着）／ `TIME`（時間制） |
| 1ゲームの基準点 | `pointsPerGame` | この点に先に達したら（2点差条件を満たせば）勝ち |
| 1マッチのゲーム数 | `gamesPerMatch` | |
| 勝利に必要なゲーム数 | `gamesToWin` | |
| 2点差ルール | `twoPointLead` | |
| デュース開始点 | `deuceFrom` | 両者がこの点で並んだらデュース。**表示用。判定には使わない** |
| 決着上限点 | `maxPoints` | **この点に達した側が、1点差でも勝ち。** `null` で上限なし |
| インターバル点 | `intervalAt` | どちらかがこの点に達したら60秒。`null` でインターバルなし |
| 制限時間（分） | `timeLimitMinutes` | `winCondition = TIME` のときのみ |

### `maxPoints` の定義を1つに固定する

**`maxPoints` は「その点を取った側が勝つ点数」とする。**

- 21点制：`maxPoints = 30`。29-29 から30点目を取った側が勝つ
- 15点制：`maxPoints = 21`。20-20 から21点目を取った側が勝つ
- `null`：上限なし。2点差がつくまで続く

「29」「20」はデュースが継続する最後の点であって、決着点ではない。
スコアとして記録され得る最大値は `maxPoints` である。バリデーションはこの定義に従う。

### 上限点は固定値にできない

第1号提供先（新日本スポーツ連盟 愛知）の実物では、**同じ団体の中で上限が3種類併存している**。

| 区分 | 要項・組み合わせ表の原文 | 上限 |
|---|---|---|
| 愛知 個人戦 4チームリーグ | 「15ポイント３ゲーム　１４オール延長2点差　最大**１７**ポイント」 | 17 |
| 愛知 個人戦 5チームリーグ | 「15ポイント３ゲーム（**打ち切り**）」 | 15（延長なし） |
| 全国 団体戦 | 「１５ポイント　１４オール延長（２点差）　最大**２１**ポイント」 | 21 |

さらに全国団体戦の要項には「**３ゲーム(運用上当日変更有)**」と明記されている。
**団体自身が、当日に採点方式が変わることを想定している。**
→ 大会開始後でも採点方式を変更できること。変更時は既入力の結果を再検証し、警告のみ出す。

**「打ち切り」は団体戦の打ち切り（`NOT_PLAYED`）とは別の意味である。**
この文脈では「延長なし・基準点先取で終了」を指す（`twoPointLead: false`）。
用語が衝突するため、UI では「延長なし」と表示する。

11点以下と時間制は、公式ルールではなくローカル大会の短縮運用である。
要項に記載がある場合のみ使う。→ Q F-6

**「予選は1ゲーム、決勝は3ゲーム」はローカル大会で最も多い運用である。**
ゲーム形式を2回選ばせず、この組み合わせ自体をプリセットにする。

| ID | 名称 | 予選リーグ | 決勝トーナメント |
|---|---|---|---|

| `qual1g-final3g-15pt` | 予選1ゲーム → 決勝3ゲーム（15点） | `15pt-1g` | `15pt-3g` |
| `uniform-21pt-3g` | 全試合 21点3ゲーム制 | `21pt-3g` | `21pt-3g` |
| `qual1g-final3g-21pt` | 予選1ゲーム → 決勝3ゲーム（21点） | `21pt-1g` | `21pt-3g` |
| `qual11pt-final15pt` | 予選11点3ゲーム → 決勝15点3ゲーム | `11pt-3g` | `15pt-3g` |

| `manual` | ステージごとに個別指定 | — | — |

大会作成時にこのプリセットを1つ選べば、以降の設定は不要。
ステージが3段階以上ある場合（予選 → 決勝T → 順位決定戦）、
**最後のステージの方式が、以降のステージへ引き継がれる。**

### 3. 表示の優先順位

**普段使わない形式を、既定の選択の邪魔にしない。**

| 段階 | 出すもの |
|---|---|
| 最初から見える | `15pt-3g` / `21pt-3g` / `15pt-1g` / `21pt-1g` |
| 「その他の形式」を開くと出る | `11pt-3g` / `11pt-1g` / `*-nocap` / `9pt-1g` / `7pt-1g` |
| 「時間制」を開くと出る | `time-10min` / `time-7min` |
| 「詳細設定」を開くと出る | `custom`（全項目を個別指定） |

11点以下と時間制は「たまにある」運用である（Q F-6）。
**使える状態は保つが、既定では畳んでおく。**

## 上書きの粒度

```
Tournament.defaultScoringRule        大会の既定値
    └─ Event.scoringRule             種目ごとの上書き（null なら継承）
         └─ Stage.scoringRule        ステージごとの上書き（null なら継承）
```

### ブロックごとに方式が違う場合

ブロック分割の直後に、**チーム数の違うブロックだけをまとめて一括変更できる**導線を出す。

```
ブロック分割の結果

  4チームのブロック  12個   採点方式  15点3G 最大17      [ 変更 ]
  5チームのブロック   3個   採点方式  15点3G 打切り ●     [ 変更 ]
                                          ↑上書き済み
```

1ブロックずつ開かせない。**チーム数でグループ化して提示する**のが、実際の運用と一致する。

### 種目ごとに方式が違う場合（Q F-9）

級別・年齢別で方式が違う大会がある。1種目ずつ開いて設定させると入力負担が跳ね上がる。

**種目 × ステージのマトリクス画面で一括編集する。**
行を種目、列をステージとし、セルに実効の採点方式を表示する。
継承しているセルは薄く表示し、上書きされたセルだけ濃く表示する。
列ヘッダ・行ヘッダをタップすれば、その行・列を一括変更できる。

→ 画面仕様は `docs/15-ui-ux.md`

**Group 単位・Match 単位の上書きは持たない。**
1つのステージ内では、必ず単一の採点方式が適用される（不変条件7）。
これにより、順位決定の集計が常に同じ母数の上で行われることが保証される。

> ### 旧版からの変更
> 初版では「上書きは Tournament → Event の2段階のみ。種目より細かく変わる大会は
> 種目を分けて登録する運用で吸収する」としていた。**これは撤回する。**
>
> 「予選リーグは1ゲーム、決勝トーナメントは3ゲーム」は同一種目内の話であり、
> 種目を分けても表現できない。しかもローカル大会では最も多いパターンである。
> 設定項目を減らす意図で決めた制約だったが、頻出パターンを潰していた。
>
> 代わりに**ステージ構成プリセット**で設定負担を吸収する。
> 運営者が選ぶのは「予選1ゲーム → 決勝3ゲーム」という1項目であり、
> ステージごとに設定させるわけではない。
> → `docs/adr/0005-scoring-15-default.md`、`docs/14-review-findings.md` F-1

## 勝敗判定

### ゲーム単位（`winCondition = POINTS`）

```
win(a, b, rule):
    hi = max(a, b)
    lo = min(a, b)

    if rule.maxPoints != null and hi >= rule.maxPoints:
        return 高い方の勝ち            # 1点差でも決着

    if hi >= rule.pointsPerGame:
        if not rule.twoPointLead:
            return 高い方の勝ち
        if hi - lo >= 2:
            return 高い方の勝ち

    return 未決着
```

`deuceFrom` は判定に使わない。UI表示とスコア入力の補助にのみ使う。
判定は `pointsPerGame` と `twoPointLead` と `maxPoints` の3つで閉じる。

### ゲーム単位（`winCondition = TIME`）

時間制では基準点が存在しない。**入力された時点のスコアが高い方が勝ち。**

```
win(a, b, rule):
    if a == b: return 未決着          # 同点。次の1点を取った方が勝ち（運用）
    return 高い方の勝ち
```

スコアの上限チェックは行わない。入力値の妥当性検証は「両者0点でないこと」のみ。

### マッチ単位

`gamesToWin` ゲームを先取した側が勝ち。
`RETIRED`（試合中の棄権）の場合、残ゲームは取得せず相手の勝ちとする。

## 混在時の検証

上書きが3段階になったことで、**同一種目内でステージごとに方式が変わるのは正規の運用**になった。
ただし次の組み合わせは不公平を生むため、検証して警告する。

| 状況 | 警告の強さ | 理由 |
|---|---|---|
| **同一ブロック内**の Match が複数の `ScoringRuleSet` を参照している | **エラー相当の強い警告** | 不変条件7の違反。順位の集計が壊れる |
| ブロックをまたいで成績を比較する（ワイルドカード・全ブロック横断の順位）のに、ブロック間で方式が違う | **強い警告** | 母数が違う。ブロック内で完結する大会なら問題ない |
| `carryOverResults = true` かつ `carryOverScope = FULL_STATS` で、予選と決勝の採点方式が異なる | **強い警告** | 母数が違う成績を混ぜることになる。`MATCH_RESULT_ONLY` への変更を提案する |
| 同一ブロック内で `gamesPerMatch` が異なる | 強い警告 | ゲーム率の母数が違う |
| ブロックのチーム数が異なるのに、勝数でブロック横断比較を行う | 警告 | 試合数が違う（4チーム=6試合 / 5チーム=10試合） |
| 順位決定基準に `pointRatio` / `pointDiff` があり、`winCondition = TIME` | 警告 | 時間制はポイント数が試合ごとに大きくぶれる |

警告であって、ブロックはしない（UX原則5）。ただし判定根拠の文章には混在の事実を明記する。

## 予選成績の持ち越し（`carryOverResults`）

予選リーグの成績を決勝リーグへ持ち越す運用がある。
このとき**採点方式が予選と決勝で異なっていても成立するよう、持ち越しの粒度を分ける。**

| `carryOverScope` | 持ち越すもの | 使う場面 |
|---|---|---|
| **`MATCH_RESULT_ONLY`** | **勝敗のみ**（勝数・勝点）。ゲーム・ポイントは決勝リーグ内の試合だけで集計 | 予選と決勝で採点方式が**異なる**とき |
| `FULL_STATS` | 勝敗・ゲーム・ポイントのすべて | 予選と決勝で採点方式が**同一**のとき |

**勝敗は採点方式に依存しない。** 15点1ゲームで勝っても21点3ゲームで勝っても、1勝は1勝である。
一方、ゲーム率とポイント率は母数が変わるため持ち越せない。粒度を分ければ両立する。

### 自動選択

運営者に選ばせない。**予選と決勝の `ScoringRuleSet` を比較して自動で決める。**

```
if 予選.scoringRule == 決勝.scoringRule:
    carryOverScope = FULL_STATS
else:
    carryOverScope = MATCH_RESULT_ONLY
    根拠に「予選と決勝で採点方式が異なるため、勝敗のみを持ち越しました」と明記する
```

手動で上書きできるが、詳細設定に隠す。

## 移行期特有の落とし穴

- **前年大会の複製（F-1-5）で採点方式も複製される。** 21点制で開催した前年の設定を複製して
  15点制の今年に使うと、気づかないまま21点で運用される。
  **複製時は採点方式だけ明示的に確認させる**
- **過去大会との数値比較ができない。** ポイント率・平均得点は方式をまたぐと意味を持たない。
  エクスポートした CSV には必ず `pointsPerGame` と `gamesPerMatch` を列として含める
- **移行期は「21点のつもりで15点のスコアシート」が現場で混ざる。**
  スコア検証で `pointsPerGame` を超える値が入力されたら、
  「この種目は15点制の設定です」と**設定値を添えて**警告する。単に「不正な値」と出さない

## 入力方式

v1 では**各ゲームの最終スコアのみ**を入力する。
ラリーごとの逐次入力（ライブスコアリング）は v2 のオプション。

### 入力の検証

| 検出 | 例（15点制・上限21） |
|---|---|
| 決着していないスコア | 15-14（2点差なし、上限未達） |
| 上限超過 | 22-20 |
| 勝者が `gamesToWin` に達していない | 15-10, 10-15 の2ゲームで終了 |
| 決着後に余分なゲームがある | 15-10, 15-8, 15-12 の3ゲーム |
| 負けた側のゲームが基準点以上 | 15-16 |
| 設定と明らかに違う点数帯 | 21-19 が入力された（21点制の設定と取り違えた可能性） |

**警告は出すが入力はブロックしない。** 現場では要項外の運用（時間短縮のための急な1ゲーム制への変更など）が起きる。
運営者が「このまま確定」を選べる経路を必ず残す。

`winCondition = TIME` では、上記のうち「両者0点」以外の検証を行わない。
