# アーキテクチャ

## 基本方針

| 項目 | 選択 | 理由 |
|---|---|---|
| 形態 | PWA（ブラウザ） | インストール不要。OS を問わない。審査なしで即時修正できる |
| データの正 | 端末内 | 通信が存在しなくても全機能が動く |
| サーバ | 任意。バックアップと閲覧ページの配信のみ | 落ちても大会は止まらない |
| 同期 | 一方向・全量スナップショット | 書き手が1台なので競合解決が不要 |
| 端末間の受け渡し | JSON ファイルのエクスポート／インポート | 通信に依存しない復旧経路を1本残す |

技術選定の詳細は未確定（ターミナルでの作業時に決定）。
ただし上記の方針を満たさない選定は不可。

## レイヤ構成

```
UI 層
  画面、入力、印刷ビュー

アプリケーション層
  ユースケース、操作履歴、Undo

ドメイン層  ← 純粋関数。外部依存を持たない
  ├ 組み合わせ生成（ブラケット、ブロック分割、シード配置、BYE配置）
  ├ 進出処理（交差配置、部分進出）
  ├ 採点判定（ゲーム／マッチの勝敗）← ScoringRuleSet を引数に取る。定数を持たない
  └ 順位決定エンジン  ← 最優先でテストする

永続化層
  端末内ストレージ、エクスポート／インポート

同期層  ← 失敗しても上位に影響を与えない
  スナップショットのアップロード
```

**ドメイン層を UI やストレージから完全に切り離す。**
順位決定エンジンは入力と出力だけを持つ純粋関数とし、単体でテストできるようにする。

**点数に関する定数をドメイン層に書かない。** `21` `30` `15` はすべて
`ScoringRuleSet` の値として引数で渡す（`docs/adr/0005`）。
grep して数値リテラルが出てきたら設計違反。

## 同期の設計

### 一方向・全量スナップショット

運営端末が1台であることを前提にすると、同期は端末からサーバへの一方向で足りる。
競合解決もマージも差分計算も不要になる。

- サーバ側は常に運営端末のスナップショットで上書きされる
- 差分同期は実装しない。大会1つ分のデータは数百 KB に収まるため、全量送信で十分
- サーバはロジックを持たない。受け取ったものを閲覧ページとして配信するだけ
- 冪等。何度送っても結果は同じ
- 認証は**公開ページの更新用トークン1本のみ**。端末内データは暗号化しない。
  トークンを紛失しても大会運営は影響を受けない（`docs/08` N-6-1）

### 動作

```
1. オフラインのまま通常どおり動作し続ける
2. ネットワークが利用可能になったことを検知
3. バックグラウンドでアップロードを試行
4. 成功 → 画面隅の表示を「同期済み HH:MM」に更新
   失敗 → 「未同期の変更 N件」に更新。それ以外は何もしない
```

同期処理は完全にバックグラウンドへ隔離する。
**同期エラーのダイアログを試合中に出す実装は不可。**

### v2 で複数端末対応する場合

本設計は書き手が1人であることに依存している。
複数端末での分担入力を実装する際は、同期層の作り直しが必要になる。
v1 でそれを見越して複雑にしない。→ `docs/adr/0003`

## 印刷

ブラウザの印刷機能で対応する。専用のプリント CSS を用意し、
A4 横向き、人数に応じたページ分割を行う。
PDF 生成ライブラリは v1 では使わない。

## 想定される障害と対応

| 障害 | 対応 |
|---|---|
| ブラウザのタブが閉じた | 再読み込みで完全復元 |
| 端末のバッテリー切れ | 別端末で JSON をインポートして継続 |
| 端末の故障 | 同上。定期バックアップからの復元 |
| 更新用トークンの紛失 | 速報の更新のみ停止。大会運営は影響なし。トークンを再発行して継続 |
| ストレージ消去 | 起動時のバックアップ促しで予防 |
| サーバ停止 | 運営に影響なし。同期のみ停止 |
| 想定外のデータでクラッシュ | 直前の状態を失わない。エラー境界で局所化する |
