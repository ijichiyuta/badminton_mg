小規模ローカル大会向けの、オフラインで動く大会集計・運営ツール。
紙のスコアシートとホワイトボードと電卓による集計を置き換えることを目的とする。

**結果のスコア表は公開されていない。**

採点方式・順位決定ルール・進行形式・出力書式まで確定している。
→ `docs/17-first-customer.md`

## 三つの制約

この3つが設計のすべてを規定している。判断に迷ったらここに戻る。

1. **全形式対応** — トーナメント、リーグ（ブロック戦）、予選リーグ→決勝トーナメント、団体戦
2. **オフラインファースト** — 通信は機能の前提条件ではない。アップロード時のみ使う
3. **1人運用** — 運営者が1人でも大会を完走できる

### C3（1人運用）の読み方

**1人運用で最も時間を奪うのは、入力ではなく中断である。**
「次いつ？何番コート？」「オーダーまだ？」「なぜこの順位？」に答える時間が、
転記の時間より長い。

機能を評価するときは「入力が何秒速くなるか」ではなく
**「中断が何回減るか」**で測る。→ `docs/13-operator-load.md`

## 採点方式

**既定は 15点3ゲーム制。** 提供先ではすでに実運用されている（移行予定ではない）。

**決着上限点は固定値にできない。** 同じ団体の中で 最大17 / 最大21 / 延長なし が併存している。
21点制をはじめ、**ゲーム形式プリセット13種**から1タップで選べる。

さらに「予選は1ゲーム、決勝は3ゲーム」という頻出運用のために、
**ステージ構成プリセット7種**を用意する。通常はこれを1つ選べば設定は完了する。

上書きの粒度は **Tournament → Event → Stage の3段階**。
Group / Match 単位は持たない（1ステージ内は必ず単一方式）。

「全部の形式に対応する」と「毎回の入力が面倒でない」は、
**柔軟性をデータモデルに持たせ、UI には出さない**ことで両立させる。
段階的開示・マトリクス一括編集・前年複製・要項テキストの貼り付けの4手。→ `docs/15-ui-ux.md`

点数に関する定数（`21` `30` `15`）をドメイン層のコードに直接書いた時点で設計違反とする。
→ `docs/adr/0005-scoring-15-default.md`

## 技術構成

```
Vite + React + TypeScript + Tailwind v4 + shadcn/ui
  + vite-plugin-pwa + Dexie(IndexedDB)   ← 大会データの正は端末内
        ↓ 電波があるときだけ一方向で送る
Supabase (ap-northeast-1) → Vercel      ← 閲覧ページのみ。v1 では P1
```

スタック台帳（`~/.claude/docs/stack-inventory.md` — リポジトリ外）の標準構成から外れるのは
**Next.js → Vite の1点だけ**。理由は `docs/adr/0007`。
