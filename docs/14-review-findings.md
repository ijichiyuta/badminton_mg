## A. 実装すれば確実にバグになる誤り

### A-1 BYE の配置先が誤っていた 🔴

**旧**：「16枠で参加13名なら BYE は3つ。位置は 1番、9番、5番（シード順位の高い側から）」

1番・9番・5番は**シード本人の位置**である。そこに BYE を置くと第1シードがブラケットから消える。

**新**：BYE は**シードの初戦の相手枠**に置く。シード位置 `p` に対し、`p` が奇数なら `p+1`、偶数なら `p-1`。
16枠13名なら 2番・15番・10番。

→ `docs/04-formats.md` 1節

### A-2 シード位置表の強弱バランスが崩れていた 🔴

**旧**：16枠で 第3・4シード = 5, 12 / 第5〜8シード = 3, 7, 10, 14

各クォーターに1名ずつ入る点は満たしていたため「動く」が、**釣り合いが取れていない**。
この配置では第5シードが第1シードと同じクォーターに入る。
正しくは第8シードが第1シードと、第5シードが第4シードと同じクォーターに入る。

**新**：標準ブラケット順を**再帰生成**する。表を持たず、4〜128 で同じ規則が使える。

```
S(2) = [1, 2]
S(2n)：S(n) の i 番目の要素 x を、i が奇数なら (x, 2n+1-x)、偶数なら (2n+1-x, x) に展開
```

`S(16) = [1,16,9,8,5,12,13,4,3,14,11,6,7,10,15,2]`（自己逆写像）

→ `docs/04-formats.md` 1節。**前年の表（Q A-7）と要突合**

### A-3 同率処理が `criteria[0]` を当該者間で再評価しなかった 🔴

**旧**：擬似コードは同率グループを分割したあと判定基準の index を **1 に戻す**としていた。
これは `criteria[0]`（勝数）を当該者間で評価しないことを意味する。

しかし日本の要項の標準文面は「**当該者間の勝敗による**」から始まる。
3者同率が当該者間の勝数で解けるケースを取りこぼす。

**新**：スコープを切り替えたうえで、必ず **index 0 から**再評価する。

→ `docs/05-ranking-engine.md`、`docs/adr/0006`。テスト T-07 がこれを検出する

### A-4 不変条件「COMPLETED な Match には勝者が存在する（BYE と WALKOVER を除く）」が誤り 🔴

没収試合（`WALKOVER`）には勝者が存在する。むしろ勝者が存在する典型である。
アサーションとして実装すると正常系で落ちる。

**新**：勝者を持たないのは `NOT_PLAYED` のみ。

→ `docs/03-domain-model.md` 不変条件2

## B. 仕様の内部矛盾・二重定義

### B-1 Match の状態が1つの enum に混ざっていた 🟠

**旧**：`PENDING` `IN_PROGRESS` `COMPLETED` と `BYE` `WALKOVER` `RETIRED` が同じ enum に並んでいた。
さらに `docs/11-data-schema.md` では `status` と `resultType` に分かれており、2つの文書が矛盾していた。

進行状態と結果種別は**直交する**（「没収試合が SCHEDULED」はあり得る）。

**新**：`status`（5値）と `resultType`（7値）に分離。`docs/11` の形を正とする。

→ `docs/03-domain-model.md`、`docs/11-data-schema.md` 変更点1

### B-2 `headToHead` と `tiebreakScope` が同じことを表していた 🟠

指標リストの `headToHead` と、設定の `tiebreakScope: AMONG_TIED` は同じ概念である。
二重化しており、組み合わせ次第で説明不能な挙動が出る。

**新**：`headToHead` を指標から**削除**。2者の直接対決は `AMONG_TIED` で `wins` を評価した結果として得る。
「3者以上では適用不可」という分岐も消える。

→ `docs/adr/0006`

### B-3 デュース上限の数値が文書間で食い違っていた 🟠

`docs/06` は「29 / 21 / 上限なし」、`docs/11` のスキーマは `maxPoints: 30`。
29 は「デュースが続く最後の点」、30 は「決着点」であり、定義が揃っていなかった。

**新**：`maxPoints` は「**その点を取った側が勝つ点数**」と定義を固定。
21点制=30、15点制=21、11点制=15。`null` で上限なし。

→ `docs/06-scoring.md`

### B-4 不変条件「進出者数 = 次ステージのエントリー数」が BYE と両立しない 🟠

3ブロック・5ブロックやワイルドカード枠では、進出者数がブラケットサイズに満たない。
`docs/04` 自身が「BYE を配置する」と書いており、矛盾していた。

**新**：**進出者数 ≤ 次ステージのブラケットサイズ**。差は BYE で埋まる。

→ `docs/03-domain-model.md` 不変条件3

## C. 現場の実態と衝突する要件

### C-1 「3タップ以内で1試合の入力が完了する」が達成不能 🟡

3ゲーム分のスコアは最大6個の数字である。タップ数では絶対に3に収まらない。
UX原則2が言っていたのは**ステップ数**だった。

**新**：画面遷移3ステップ以内／1試合15秒以内／10試合の連続転記3分以内。

→ `docs/07` F-5 性能目標、暫定決定 P-14

### C-2 「1ブロックでも未完了なら決勝トーナメントは開始できない」 🟡

UX原則5「システムが正しさを主張して大会を止めることは最悪の失敗」に反する。
先に終わったブロックから決勝の一部を始めるのは、ローカル大会では通常運転である。

**新**：**部分進出**を既定で許可。未確定枠は「A組1位（未確定）」として保持し、警告は出すが止めない。

→ `docs/04-formats.md` 3節、`docs/07` F-7-3〜F-7-5、暫定決定 P-10

### C-3 「大会データは管理者パスワードで保護する」が1人運用の単一障害点 🟡

パスワードを忘れた瞬間に大会が止まり、復旧できる人が他にいない。

**新**：端末内データに**パスワードをかけない**。認証は公開ページの更新用トークン1本のみ。
紛失しても大会運営は影響を受けない。

→ `docs/08` N-6-1、暫定決定 P-11

### C-4 `rankings` を永続化していた 🟡

順位は再計算可能な派生データ。保存するとルール設定変更時に保存値と再計算値が食い違う。

**新**：`rankingsCache` に改名し、`ruleSetHash` を持たせる。不一致なら破棄して再計算。
`provisional`（暫定）フラグも追加し、**リーグ途中の順位を「確定」と表示しない**。

→ `docs/11-data-schema.md` 変更点7

## D. 抜け落ちていた要件

### D-1 団体戦の運用機能がなかった 🟠

編成パターンと打ち切りの仕様はあったが、**オーダーの提出状態**が存在しなかった。
「オーダー未提出のまま Tie が SCHEDULED」という、現場で最も待ちが発生する状態が表現できない。

**新**：`Tie.lineupStatus`（未提出／片側のみ／両者提出済み）を追加。
機能要件に **F-12 団体戦の運用**（10項目）を新設。オーダー未提出チームをホーム画面に常時表示。

→ `docs/07` F-12、`docs/11-data-schema.md` 変更点8

### D-2 採点方式の混在検証がなかった 🟠

種目単位で採点方式を上書きできる設計なのに、
**15点制と21点制の試合が同一ステージに混在した場合の不公平**が考慮されていなかった。
ポイント率もゲーム率も母数が変わる。

**新**：混在を検知して警告。率系の指標を使う場合は強い警告。
Match に `scoringRuleId` を持たせて検知可能にする。CSV 出力に `pointsPerGame` を含める。

→ `docs/06-scoring.md`、`docs/07` F-6-8

### D-3 ペアの片方だけ欠場が表現できなかった 🟡

Entry の状態が `ACTIVE | WITHDRAWN` のみ。ローカル大会では常に起きる事態。

**新**：`SUBSTITUTED` を追加。**Entry の id を保持したまま `playerIds` を差し替える**
（Match の参照を壊さないため）。変更は `operationLog` に残す。

→ `docs/03-domain-model.md`、暫定決定 P-13、Q C-8

## F. 自分の判断の撤回

### F-1 採点方式の上書き粒度を2段階に制限したのは誤りだった 🔴

**このレビューで一度決めたことを、同じ日に撤回している。**

初版レビューの時点で、`docs/adr/0005` の決定4として
「上書きは Tournament → Event の2段階のみ。種目より細かく方式が変わる大会は、
種目を分けて登録する運用で吸収する」と定めた。設定項目を増やさないための制約だった。

**これは「予選リーグは1ゲーム、決勝トーナメントは3ゲーム」という
ローカル大会で最も多い運用を、表現不可能にしていた。**
予選と決勝は同一種目の中の話であり、種目を分けても表現できない。

**訂正**：採点方式の上書きを **Tournament → Event → Stage の3段階**にする。
Group / Match 単位は引き続き持たない（1ステージ内は単一方式。不変条件7）。

設定負担については、**制約の置き場所を間違えていた**。
制限すべきは上書きの粒度ではなく、運営者に見せる設定の数である。
代わりに2階層のプリセットで吸収する。

| 階層 | 選ぶもの | 種類 |
|---|---|---|
| ステージ構成プリセット | 大会全体でどう使い分けるか | 7種 |
| ゲーム形式プリセット | 個別のステージに何を当てるか | 13種 |

通常はステージ構成プリセットを1つ選べば設定は完了する。

→ `docs/06-scoring.md`、`docs/adr/0005` 改訂履歴、暫定決定 P-12

#### 併せて追加したもの

| 内容 | 理由 |
|---|---|
| `winCondition: POINTS \| TIME` | 「10分1本勝負」は大人数の予選で実在する。判定は「スコアの高い方が勝ち」だけで済み、実装コストが小さい |
| `carryOverResults` × 方式相違 の警告 | 予選の成績を決勝リーグへ持ち越すのに母数が違うと、ゲーム率・ポイント率が破綻する |
| 検証警告に設定値を添える | 移行期は「21点のつもりで15点の設定」が必ず起きる。「不正な値」とだけ出すと運営者が原因を特定できない |

## G. 一次資料による訂正（2026-09-13 追記）

第1号提供先が **新日本スポーツ連盟 愛知バドミントン協議会** に確定し、
公開されている要項・組み合わせ表・タイムテーブルの現物を入手した。
**推測で置いた暫定決定のうち3件が誤りだった。**

### G-1 15点制の上限を 21 と決め打っていた 🔴

**旧（P-02）**：15点制の決着上限点を 21 と仮置き。

**実物**：同じ団体の中で**3種類が併存していた**。

| 区分 | 原文 | 上限 |
|---|---|---|
| 愛知 個人戦 4チームリーグ | 「１４オール延長2点差　最大**１７**ポイント」 | 17 |
| 愛知 個人戦 5チームリーグ | 「15ポイント３ゲーム（**打ち切り**）」 | 15（延長なし） |
| 全国 団体戦 | 「１４オール延長（２点差）　最大**２１**ポイント」 | 21 |

**訂正**：上限は固定値にできない。プリセットを3種（cap21 / cap17 / 延長なし）用意する。

**「点数をハードコードしない」という判断自体は正しかった**が、
上限だけは1つに決められると思っていた。それが誤りだった。

### G-2 第3基準を「率」だと思っていた 🔴

**旧（P-03）**：`criteria = [wins, gameRatio, pointRatio]`

**実物**：

> リーグ戦にて勝敗数が同じ場合はゲーム勝率にて、ゲーム勝率が同じ場合は**得失点差**にて順位を決定します。

**ゲームは「率」、ポイントは「差」で混在していた。**

**訂正**：`criteria = [wins, gameRatio, **pointDiff**]`。
「率と差は別物なので両方実装する」という初版の判断が、ここで効いた。

### G-3 「当該者間で再計算する」と決め打っていた 🔴

**旧（P-04）**：`tiebreakScope = AMONG_TIED`。
「日本の要項の標準文面は『当該者間の勝敗による』から始まる」という前提で決めていた。

**実物**：**この大会の要項には「当該者間」に相当する記載が一切ない。**
素直に読めば全試合の成績（`ALL_MATCHES`）である。

**訂正**：既定を `ALL_MATCHES` に変更。

ただしこれで解決したわけではない。**要項には次も書かれていない。**

- 3者以上が同率になった場合の規定
- 得失点差まで同じ場合の規定
- 棄権者が出た場合の扱い

**各ブロック1位・2位を表彰するため、2位を必ず決める必要がある。同率処理は毎回起きる。**
→ `AMONG_TIED` と `ALL_MATCHES` で順位が変わるデータを検知したら両方を提示し、
   運営者が要項の解釈を決められるようにする。
→ **Q E-9（過去に揉めた実例）が最重要の未回答項目になった。**

### G-4 Group 単位の上書きを「持たない」と決めていた 🟠

**このレビューで、同じ判断を2回撤回している。**
初版で Event 単位までと決め、同日に Stage 単位まで広げ、さらに Group 単位まで広げた。

**実物**：同じ種目（男子3部）の中で、ブロックによって採点方式が違う。

| ブロック | チーム数 | 採点方式 |
|---|---|---|
| 1ブロック | 5 | 15点3ゲーム **打ち切り（延長なし）** |
| 2〜4ブロック | 4 | 15点3ゲーム 14オール延長 最大17 |

**試合数が多いブロックだけ延長をなくして時間を詰めている。**

**訂正**：上書きを Tournament → Event → Stage → **Group** の4段階にする。
不変条件7を「1つの **Group** 内は単一の採点方式」に緩める。
リーグ戦の順位はブロック内でのみ比較するため、ブロック間の差は不公平を生まない。

### G-5 抜けていた要件（実物から判明）

| # | 抜け | 対応 |
|---|---|---|
| 1 | **編成パターンに「3複」がない** | 3複（D-D-D）を追加。第1=女子D／第2=男子D／第3=混合D |
| 2 | **Tie 内の各試合に種別制約がある概念がない** | `slotConstraints` を追加。オーダー入力時に検証 |
| 3 | **打ち切りを Tie が持っていた** | Stage へ移す。「予選は全試合消化・決勝は2勝先取」が同一大会内で起きる |
| 4 | **審判の割当機能がない** | F-13 を新設。敗者審の自動割当が要項でルール化されている |
| 5 | **試合番号が1種類しかない** | 通し番号とブロック内試合順の2つを持つ。現行の星取表が両方を印字している |
| 6 | タイムテーブルの事前生成が P1 だった | **P0 へ**。現行運用の中核であり、審判割当もこれに紐づく |

### この節から得られた教訓

**要項の原文を手に入れる前に、順位決定と採点方式の細部を決めてはいけない。**
初版で「E-1（要項原文）が最優先」と書いたのは正しかったが、
それを待たずに暫定決定を積み上げた結果、3件を訂正することになった。

一方で、**設定可能にしておいた箇所は1つも壊れなかった。**
「率と差の両方を持つ」「点数をハードコードしない」「上書き粒度を広げられる構造にする」は、
いずれも実物と合わなかったときに設定値の変更だけで吸収できた。

## 今回の方針変更

指摘対応と並行して、**制約 C3（1人運用）を独立した設計文書に格上げ**した。

- 負担を5つ（設定・準備・入力・判断・**中断**）に分解
- **最大の負担は入力ではなく中断である**ことを明示
- 機能要件の各項目に「どの負担を減らすか」の欄を追加。**空欄の要件は入れる理由を説明できていない**
- UX 原則に「運営者に決めさせない」「中断を減らすことを速くすることより優先する」を追加

→ `docs/13-operator-load.md`
