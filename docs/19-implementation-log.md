### 実装して見つけた不具合2件

**どちらも「同じミリ秒に2件発生すると区別できない」という同じ原因だった。**

**1. Undo が別の試合を戻す**

操作ログを `at`（ISO時刻）で並べて「直近の取り消せる操作」を選んでいた。
しかし**連続入力モードでは複数の結果入力が同じミリ秒に入る**。
時刻が同値になると順序が決まらず、トーストの「取り消す」が
1つ前の試合を戻してしまう。

連続入力は本製品の核となる機能（O-3-1）なので、**本番で必ず踏む**。
大会内で単調増加する `seq` を持たせ、トランザクション内で採番するよう修正した。

**2. バックアップが上書きされる**

`bk-${tournamentId}-${Date.now()}` を id にしていたため、
同じミリ秒に2回取ると同じ id になり、2件目が1件目を上書きしていた。
テストで「2件取ったのに1件しかない」として露出した。

こちらも `seq` を持たせて解決。**一度 base36 の文字列で並べる実装にしたが、
`z` と `10` の大小が逆転するため数値の連番に揃え直した。**

### Undo は逆操作を計算しない

変更前後のレコードをそのまま `OperationRecord.before` / `after` に持ち、
取り消し時は**変更前のレコードを書き戻すだけ**にした。

大会1つ分のデータが数百KBに収まるため、この素朴な方法が最も壊れにくい。
逆操作を計算する方式は、操作の種類が増えるほど間違いが入る。

### 採点方式の解決は4段階

`Group → Stage → Event → Tournament` の順に解決する `effectiveScoringRuleId` を実装し、
4段階すべてをテストで固定した。ブロック単位の上書きが最優先になる。

### 「確定できるまで待つ」の判定

自動フォーカス移動には「その数字がこれ以上伸びないか」の判定が要る。

### ファイル保存で「不利な点1」を消した

ブラウザの保存領域は「サイトデータを消去」で飛ぶ。これが旧サービス（Windowsアプリ）に対する
構造的な弱点だった。

**File System Access API で実際のファイルに直接書き込める。**
保存先を1回選んでもらえば、以降は1試合入力するたびに同じファイルへ上書きする。
Windows / Mac の Chrome・Edge で動作し、**旧サービスと同等**になる。

Safari と Firefox は非対応なので、定期的な書き出しにフォールバックする。
あわせて `navigator.storage.persist()` を必ず呼び、容量不足による自動削除から守る。

### 複数端末は「リアルタイム同期」ではなく「担当分け＋合流」

電波がなければ端末間通信は原理的にできない。ブラウザはサーバになれない。
**しかし同じ試合を2人が同時に入力することはない。担当が分かれている。**

```
端末A（メイン）… 男子1〜3部
端末B（サブ）  … 女子2〜3部
      ↓ JSON を渡す（USB / AirDrop / メール / 電波があればサーバ経由）
    1つの大会データ
```

試合ごとに書き手が1人なら、合流は自明に計算できる。
片方だけが入力していればそれを採り、両方が入力していて内容が違う場合だけ衝突として返す。
**電波が一切なくても成立する。**

`validateAssignments` で担当の重複を事前に検出する。
**重なっていなければ衝突は構造的に起きない。** これが合流を単純に保つ唯一の方法。

### スコアシートはフルグリッド版

記入例の構造をそのまま再現した。4行 × N列 × ゲーム数。
列数は `maxPoints × 2 + 2` で計算する（15点制・上限17なら35列、21点制・上限30なら61列）。

**審判欄には敗者審の割当を自動で印字する。** 紙に出ていれば当日聞かれる回数が減る（O-5）。

QRコードは見送った。外部ライブラリを足すか自前実装するかになるが、
同等の体験は「試合番号を打つ」で足りており、実装の危険を先に取る理由がない。

### 「公式のスコアシート様式」は存在しない

「本当に公式か」と問われて調べ直した結果、**日本バドミントン協会は紙のスコアシートの
統一様式を配布していない**ことが分かった。

[審判ページ](https://www.badminton.or.jp/corporate/concerned/referee)にあるのは
ルールブック・審判員規程・各種申請書類（様式R1号・S1〜S11号）だけで、
**スコアシートの様式は1つもない**。代わりに置かれているのが
**BIRD SCORE 審判入力「練習版」案内** ＝ 協会は電子入力を推している。

規程が定めているのは**用紙のレイアウトではなく記入方法**。

> ②**スコアシートを使用する場合**、両サイドの最初の点数として「０」を書き、
> そして、サーバーには「S」を指定のマスに書くこと。
> ダブルスの場合は合わせて「R」を指定のマスに書くものとする。
> （BAJルールブック2026 公認審判員規程）

> 主審は「プレー イズ サスペンディッド」とコールし、そして**タッチパネルに"S"を入力する。
> または、スコアシートの所定の位置に"S"を記入する。**

「使用する場合」「使用されている場合」という条件付きで、**紙自体が任意**であり
電子入力が並列の選択肢として書かれている。
大会運営規程にあるのも「棄権・失格のときの記入参考例」だけで、レイアウトの規定はない。

| 出所 | 位置づけ |
|---|---|
| 日本バドミントン協会 | **様式を配布していない**。記入方法だけ規定 |
| 岡山県高体連の記入例 | 県高体連の書式 |
| 大田区バドミントン協会 | 自サイトに「**大田区の書式**に合わせた」と明記 |
| takeorilab | 個人サイト。「公式フォーマット」は**自称** |

**実装は「公式準拠」ではなく「一般的な様式に沿ったもの」。**
ただし規程が定める記入方法（0の記入・S/R欄・終了時刻とマッチ時間）は満たしている。

**本当に合わせるべきは第1号提供先が実際に使っている用紙。**
新スポ連愛知の組合せ表には「審判用紙は敗者が速やかに本部に返却してください」とあり、
独自の用紙が存在する。→ Q A-7 に追記した。

## 2026-09-14 実データ検証その2：愛知県社会人クラブリーグ（団体戦）

新スポ連（個人戦・94試合のタイムテーブル再現）に続く、**2本目の受入テスト**。
今度は系統が違う。JBA 系・団体戦・2複1単・順位決定基準が要項に明記されている。

出典：第101回愛知県社会人クラブチーム対抗選手権（前期リーグ戦）男子1部、6チーム総当たり。

### 要項（内規14）の順位決定基準

```
1. 勝敗による
2. マッチ得失率による
3. ゲーム得失率による
4. ポイント得失率による
5. 上記1〜4で決まらない場合は当事者同士で勝った方
```

### 結果：公表順位と完全一致（17テスト）

マッチ得失・ゲーム得失・ポイント得失の全チーム分、および最終順位1〜6位すべてが一致。
抽選には一度も落ちていない（`DRAW_USED` 警告なし）。

### この検証が見つけた設計の穴、2つ

**穴1：`unresolvedAction` に `HEAD_TO_HEAD` がなかった。**
「決まらない場合は当事者同士」は `tiebreakScope: 'AMONG_TIED'` では表現できない。
`AMONG_TIED` は**すべての**指標を当該者間で見るが、この要項は
1〜4を全試合で見て、**使い切ってから**当事者同士を見る。適用のタイミングが違う。
→ `UnresolvedAction` に `HEAD_TO_HEAD` を追加。決まらなければ同順位にし、抽選には落とさない。

**穴2：`isTeamEvent` が宣言だけで未実装だった。Tie 階層が潰れていた。**
要項が「1. 勝敗 2. マッチ得失率」と2段構えで書く理由は、団体戦では両者が別物だから
（2複1単なら1対戦=3マッチ）。`docs/05` には最初からこの階層が書いてあったが、
`ranking.ts` が Match 単位でしか数えていなかったため、第2基準が第1基準と同じ値になり死んでいた。
→ `EntryStats` に `matchesWon` / `matchesLost` を追加し、`wins` / `losses` を Tie 単位に。
`Match.tieId` で Tie を束ね、`tieId === null` なら1試合を1 Tie とみなす。
これで個人戦は `wins === matchesWon` になり、既存374テストは一切壊れなかった。

**仕様に書いてあっても実装されているとは限らない。実データを通して初めて分かった。**

### プリセット追加

`team-league-aichi`：「勝敗 → マッチ率 → ゲーム率 → ポイント率（決まらねば当事者同士）」。
団体戦リーグの標準形。テストはこのプリセットを**そのまま**使う（テスト用に組み立て直さない）。

### テストデータ組み立てで自分が踏んだ罠

公表されているのは集計値（マッチ数・ゲーム数・ポイント数）だけなので、
そこから Match を逆算して組み立てた。2回間違えた。

1. ゲーム数合わせのダミーが得点にも乗り、合計が21点多くなった
2. 得点を1ゲーム目に寄せたら、**負けたゲームに勝者側の得点が乗って**ゲーム得失が狂った

正しくは「**取ったゲームに自分の得点を、落としたゲームに相手の得点を寄せる**」。
どちらもテスト側の誤りで、エンジンは正しかった。

### BIRD SCORE 調査（`docs/18-incumbent.md` §7.1 に反映）

競合表で「リアルタイムスコア表示システム」と書いていたのは誤り。
**日本バドミントン協会監修**、2021年3月リリース、第74回全日本総合から公式採用。
審判入力だけでなく大会運営機能（選手リスト・PDF出力・サイト管理・進行管理・レフェリーコール）を統合。

→ **「電子化」は価値の主張にならない。**全国大会ではすでに標準。
差は要項の多様性を吸収する**設定可能性**と、1人運用の負担削減に置く。
BIRD SCORE が降りてこないローカル層がこのシステムの居場所。

## 2026-09-14 実データ検証その3：愛知県社会人リーグ 男子全24部

1部だけの検証（その2）は公表集計値から Match を逆算していた。
今回は**速報ページの全ゲームスコアをそのまま入力**して、集計値と順位の両方を突き合わせた。

### 出典を2つ使い、互いに検証した

**個人名は書き出していない。**リポジトリが公開なので、チーム名（団体名）とスコアだけにした。

### この規模で流して初めて出た問題、4つ

**1. 要項の第1基準「勝敗」が criteria から抜けていた。順位が実際に入れ替わっていた。**

活用形の閉じ方の誤り。参加者に見せる文なので直した。
