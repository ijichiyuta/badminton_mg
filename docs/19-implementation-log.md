### 実装して見つけた不具合2件

**どちらも「同じミリ秒に2件発生すると区別できない」という同じ原因だった。**

**1. Undo が別の試合を戻す**

操作ログを `at`（ISO時刻）で並べて「直近の取り消せる操作」を選んでいた。
しかし**連続入力モードでは複数の結果入力が同じミリ秒に入る**。
時刻が同値になると順序が決まらず、トーストの「取り消す」が
1つ前の試合を戻してしまう。

連続入力は本製品の核となる機能（O-3-1）なので、**本番で必ず踏む**。
大会内で単調増加する `seq` を持たせ、トランザクション内で採番するよう修正した。

**2. バックアップが上書きされる**

`bk-${tournamentId}-${Date.now()}` を id にしていたため、
同じミリ秒に2回取ると同じ id になり、2件目が1件目を上書きしていた。
テストで「2件取ったのに1件しかない」として露出した。

こちらも `seq` を持たせて解決。**一度 base36 の文字列で並べる実装にしたが、
`z` と `10` の大小が逆転するため数値の連番に揃え直した。**

### Undo は逆操作を計算しない

変更前後のレコードをそのまま `OperationRecord.before` / `after` に持ち、
取り消し時は**変更前のレコードを書き戻すだけ**にした。

大会1つ分のデータが数百KBに収まるため、この素朴な方法が最も壊れにくい。
逆操作を計算する方式は、操作の種類が増えるほど間違いが入る。

### 採点方式の解決は4段階

`Group → Stage → Event → Tournament` の順に解決する `effectiveScoringRuleId` を実装し、
4段階すべてをテストで固定した。ブロック単位の上書きが最優先になる。

### 「確定できるまで待つ」の判定

自動フォーカス移動には「その数字がこれ以上伸びないか」の判定が要る。

### ファイル保存で「不利な点1」を消した

ブラウザの保存領域は「サイトデータを消去」で飛ぶ。これが旧サービス（Windowsアプリ）に対する
構造的な弱点だった。

**File System Access API で実際のファイルに直接書き込める。**
保存先を1回選んでもらえば、以降は1試合入力するたびに同じファイルへ上書きする。
Windows / Mac の Chrome・Edge で動作し、**旧サービスと同等**になる。

Safari と Firefox は非対応なので、定期的な書き出しにフォールバックする。
あわせて `navigator.storage.persist()` を必ず呼び、容量不足による自動削除から守る。

### 複数端末は「リアルタイム同期」ではなく「担当分け＋合流」

電波がなければ端末間通信は原理的にできない。ブラウザはサーバになれない。
**しかし同じ試合を2人が同時に入力することはない。担当が分かれている。**

```
端末A（メイン）… 男子1〜3部
端末B（サブ）  … 女子2〜3部
      ↓ JSON を渡す（USB / AirDrop / メール / 電波があればサーバ経由）
    1つの大会データ
```

試合ごとに書き手が1人なら、合流は自明に計算できる。
片方だけが入力していればそれを採り、両方が入力していて内容が違う場合だけ衝突として返す。
**電波が一切なくても成立する。**

`validateAssignments` で担当の重複を事前に検出する。
**重なっていなければ衝突は構造的に起きない。** これが合流を単純に保つ唯一の方法。

### スコアシートはフルグリッド版

記入例の構造をそのまま再現した。4行 × N列 × ゲーム数。
列数は `maxPoints × 2 + 2` で計算する（15点制・上限17なら35列、21点制・上限30なら61列）。

**審判欄には敗者審の割当を自動で印字する。** 紙に出ていれば当日聞かれる回数が減る（O-5）。

QRコードは見送った。外部ライブラリを足すか自前実装するかになるが、
同等の体験は「試合番号を打つ」で足りており、実装の危険を先に取る理由がない。

### 公開範囲は「残すものを列挙する」方式にした

`redact()` は元のオブジェクトから項目を削るのではなく、
**`id` / `tournamentId` / `name` / `affiliation` の4つだけを持つ新しいオブジェクトを作る。**

削る方式だと、将来フィールドが増えたときに漏れる。
残す方式なら、増えたフィールドは自動的に公開されない。

`Player.note` を型に足した。名簿の取り込み元によっては**連絡先や住所が紛れ込みうる**ためで、
テストで「note が落ちること」を固定してある。更新用トークンと操作ログも送らない。

### 閲覧ページの主役は「自分の次の試合」

要項に「当日のプログラム配布はありません」と明記されており、
**選手が自分の端末で見る前提がすでにある**。

選手名で検索すると、次の試合の**コート番号と目安時刻**が最初に出る。
大会全体の結果一覧は折りたたみの中に置いた。
「次いつ？」「何番コート？」に先回りするのが目的であり、
結果一覧はその後でよい（O-5-1）。

時刻は「だいたい○時ごろ」と幅を持たせて表示する。**正確な時刻を約束しない。**

### 名簿の取り込みは列の役割を推定する

タブ区切り（Excel）とカンマ区切り（CSV）の両方を受ける。
クラブ名・学校名らしい語（クラブ / 高校 / BC など）で所属列を、
数字だけの列でシード列を判定する。推定が外れたら手で直せる。

人数が揃っていない・同姓同名がある場合は警告を出すが、**取り込みはブロックしない**（UX原則5）。
