### 実装して分かったこと

**1. BYE の勝敗集計が抜けていた（実装のバグ）**

不戦勝は片側のエントリーが `null` であるため、集計ループの
「両側が存在する試合だけ処理する」というガードに引っかかって
**1勝としてカウントされていなかった**。

`resultType === 'BYE'` を先に分岐させ、勝者の1勝として数えたうえで
ゲーム率・ポイント率の分母には入れない扱いに修正。
当該者間（`AMONG_TIED`）の集計には相手がいないため現れない。

**2. docs/05 の T-07 は5名では成立しない**

「5名リーグ、3名同率 → 当該者間の勝数で2名と1名に分割」と書いてあるが、
3者の総当たり（3試合）で得られる勝数は (2,1,0) か (1,1,1) しかなく、
**2名と1名の分割は構造的に起きない**。

テストは6名リーグ・4名同率が 2+2 に分割される形に変更した。
`criteria[0]` から再評価しないと取りこぼす、という検証の意図は保たれている。
→ `docs/05-ranking-engine.md` の T-07 の記述を後で直す。

**3. 上限点が設定値であることの効き目**

`judgeGame(17, 16)` は 上限17 の設定では決着、上限21 の設定では未決着になる。
同じスコアが設定次第で意味を変えるため、**検証メッセージに設定値を添える**
要件（F-5-12）が効く。テストでも両方を突き合わせている。

### 実装して分かったこと

**1. `docs/04-formats.md` の「検証済みの性質」をそのままテストにできた**

自己逆写像・1回戦の和が `N+1`・各クォーターのシード番号和が等しい の3つを
4/8/16/32/64/128 の全サイズで検証している。初版で崩れていた
「クォーター間のバランス」が回帰テストとして固定された。

**2. 対戦順序は現行の組合せ表から読み取って実装した**

実際の星取表のマスから、丸数字と対戦の対応を復元できた。

```
4チーム：① 1-2 / ② 3-4 / ③ 1-3 / ④ 2-4 / ⑤ 1-4 / ⑥ 2-3
5チーム：① 1-2 / ② 3-4 / ③ 1-5 / ④ 2-3 / ⑤ 4-5 / ⑥ 1-3 / ⑦ 2-4 / ⑧ 3-5 / ⑨ 1-4 / ⑩ 2-5
```

**`docs/04-formats.md` の記述（4名：(1-4)(2-3) (1-3)(2-4) (1-2)(3-4)）とは並びが違う。**
星取表のマスに入る番号が変わると「去年と表が違う」と現場で指摘されるため、
**現行の並びを正とする**。表にない人数は巡回法（サークルメソッド）に落ちる。

**3. 「連続出場を避ける」の意味を取り違えていた**

4チームの並びでは ② 3-4 の次が ③ 1-3 で、選手3が連続する。
最初これをバグだと考えたが、**タイムテーブルを見ると ①② は2コートで同時進行**しており、
「連続する2試合」は時間的には並行だった。

検証すべき性質は「**同一ラウンド内で重複しないこと**」。
`roundsOf(pairings, perRound)` / `roundsAreDisjoint()` を追加してテストし直した。
タイムテーブル生成でもこの切り分けをそのまま使う。

### 実装して分かったこと

**1. 現行のタイムテーブルは「ラウンド優先」で並んでいる**

実物を読み直すと、全ブロックが①②を消化してから③④へ進む構造だった。

```
9:30   男3部1①  男3部1②  女3部1①  女3部1②  女3部2①  女3部2②
10:00  女3部3①  女3部3②  男1部①   男1部②   男2部1①  男2部1②
...
11:30  女2部2①  女2部2②  男3部1③  男3部1④  女3部1③  女3部1④
                          ↑ここで全ブロックの①②が終わり③④へ
```

ブロック優先（1ブロックを最後まで流す）ではない。
`buildSchedule` はこのラウンド優先の並びを再現する。

**2. 規模の見積もりが要項と一致した**

60組を4チーム×15ブロックに分けると **90試合**。6コートなら **15枠**。
9:30開始・30分刻みで最終枠が **16:30** になる。
要項の「9:00受付／9:30開始」「昼食時間はとりません」と整合する。
**モデルが現実と合っていることの傍証になった。**

**3. 審判割当はアルゴリズムとして書ける**

> ① 第一試合の審判はタイムテーブル3段目の選手でお願いします。
> ② 敗者審を原則とします。（敗者2名、勝者1名は線審を担当）

第1枠は「3段目 = 6コート×3枠先」の試合の選手、
第2枠以降は「同じコートの1つ前の試合」の敗者2名＋勝者1名。
`assignReferees` で全試合分を出せる。**紙に印字すれば当日聞かれる回数が減る**（O-5）。

`/code-review high 60d90e8..HEAD` を実行。**確認済みの不具合が8件出た。**
うち6件は同じイテレーションで並行して気づいて直していたもの、2件は監査だけが見つけたもの。
**すべて実際にコードを走らせて再現が確認されている。**

| # | 深刻度 | 内容 |
|---|---|---|
| 1 | HIGH | `buildSchedule` がラウンド境界を無視してコートに詰め、**同一エントリーが同時刻に複数コートへ**入る |
| 2 | HIGH | 3チームブロックの対戦順が同時2試合になり、同じ選手が2コートに出る |
| 3 | MEDIUM | 審判割当の「N段目」が1段ずれる（3段目のつもりが4段目） |
| 4 | MEDIUM | `buildBracket` に `size` を明示するとエントリーが**無言で消える** |
| 5 | MEDIUM | `byePositions` が要求数に届かず「選手もBYEもない枠」が残る |
| 6 | MEDIUM | `perGroup` 指定が「4と5の混在」ではなく「4と3の混在」になる |
| 7 | LOW | `parseTime` が `9:75` を通す。`courtCount: 0` で `NaN` 試合が生成される |
| 8 | LOW | `toTimetable` が範囲外コートの試合を黙って落とす |

### いちばん効いた指摘

**#1 は自分のテストが構造的に見逃していた。**
テストを15ブロック（1ラウンド30試合）でしか書いていなかったため、
1ラウンドの試合数が常にコート数を超えていて詰め込みの不具合が表に出なかった。

```
4チーム1ブロック → 6試合すべて 09:30
#1 c1 a-1 vs a-2 / #3 c3 a-1 vs a-3 / #5 c5 a-1 vs a-4
```

**`validateSchedule` が自分の生成物を不正と判定する状態**だった。
実装ログ #2 に「検証すべき性質は同一ラウンド内で重複しないこと」と書いておきながら、
生成側がそれを満たしていなかった。

修正：枠ごとに「すでにその枠にいるエントリー」を持ち、衝突する試合は次の枠へ送る。
1〜15ブロック × 3〜6チームの全組み合わせで衝突ゼロを回帰テストにした。

**#2 は「1ブロックの同時試合数」を固定2にしていたのが原因。**
正しくは `floor(チーム数 / 2)`。4・5チームなら2、3チームなら1。
現行大会が4・5チームしか使わないため、たまたま2で合っていた。

**#6 は要項の読み違い。**
`Math.ceil` はブロック数を増やして端数を**小さい**ブロックにする。
現行大会は「4チームリーグ・5チームリーグ」なので端数は**大きい**ブロックに吸収される。
`remainderPolicy: 'ABSORB' | 'SPLIT'` を追加し、既定を ABSORB にした。
62組・4人ずつ → 5人×2 + 4人×13。

### 実装して見つけた不具合2件

**どちらも「同じミリ秒に2件発生すると区別できない」という同じ原因だった。**

**1. Undo が別の試合を戻す**

操作ログを `at`（ISO時刻）で並べて「直近の取り消せる操作」を選んでいた。
しかし**連続入力モードでは複数の結果入力が同じミリ秒に入る**。
時刻が同値になると順序が決まらず、トーストの「取り消す」が
1つ前の試合を戻してしまう。

連続入力は本製品の核となる機能（O-3-1）なので、**本番で必ず踏む**。
大会内で単調増加する `seq` を持たせ、トランザクション内で採番するよう修正した。

**2. バックアップが上書きされる**

`bk-${tournamentId}-${Date.now()}` を id にしていたため、
同じミリ秒に2回取ると同じ id になり、2件目が1件目を上書きしていた。
テストで「2件取ったのに1件しかない」として露出した。

こちらも `seq` を持たせて解決。**一度 base36 の文字列で並べる実装にしたが、
`z` と `10` の大小が逆転するため数値の連番に揃え直した。**

### Undo は逆操作を計算しない

変更前後のレコードをそのまま `OperationRecord.before` / `after` に持ち、
取り消し時は**変更前のレコードを書き戻すだけ**にした。

大会1つ分のデータが数百KBに収まるため、この素朴な方法が最も壊れにくい。
逆操作を計算する方式は、操作の種類が増えるほど間違いが入る。

### 採点方式の解決は4段階

`Group → Stage → Event → Tournament` の順に解決する `effectiveScoringRuleId` を実装し、
4段階すべてをテストで固定した。ブロック単位の上書きが最優先になる。
